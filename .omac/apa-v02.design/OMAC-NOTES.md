## 1 工作分组与依赖

分组与设计 §20.3 一致。这里补的是拆 DAG 时用得上的东西：依赖边、能并行的地方、每组里建议单独成节点的部分。

### 1.1 关键路径

```
W0 契约定稿 ──► 账本结构版本 3 ─┬─► W1 规则补齐与归属 ───────────────────┐
                              │                                        ▼
                              └─► W2 两端点与级联 ──► W3 留痕与计数 ──► W4 积压放开
```

- **最长链是 W0 → W2 → W3 → W4。** W1 与 W2 在 W0 之后并行，W1 只在 W4 汇合。
- **其他组不得成为这条链的前置。** W5–W13 都只依赖 W0（个别依赖见下表），可以与关键路径并行，但在排期、评审和合并冲突的取舍上让路。
- **W1 的收益不等 W2。** "积压只跑规则"不需要任何模型端点，W1 合入主干后，已有部署里结构化的那部分积压就能先被处置。这不是拆小版本：发布仍是一次，只是关键路径上的节点按能独立验收的粒度切。
- **W4 在合成夹具上用替身验完即可关闭。** `ACT-BKL` 的结论（不确定带起始值、带内占比）要在真实积压上得出，归本机升级验证 L5（设计 §21.3），不在本轮 OMAC 范围，也不卡 W4 或 W14。

### 1.2 建议在 W0 之后先落一个"账本结构版本 3"节点

设计要求迁移只增不改、数据结构版本随发行只增，发布物里 `schema.ledger` 是 3（附录 B.5）。各组都要加表或加列（判断记录、计划日期、进展、建议信息、外发范围、默认项目、指标上一次取值、合并键、静音、登录会话的有效期等）。建议把它们收进同一次迁移，在 W0 之后、各组开工之前单独成一个节点。

理由：

- 各组各加一次迁移，主干上会出现版本 3、4、5 多个中间版本；跟着主干跑的已有部署要么经历多次迁移，要么等到最后才能升级，后者正好把关键路径卡住。
- 结构先定，各组的节点互不改同一个迁移文件，合并冲突少。
- 升级演练（第 5 节）只需要验证版本 2 → 3 这一步。

代价是 W0 要把所有组的存储结构想清楚。设计 §6 已经给出字段，够用。

**已决定（第 7 节问题 2）：已有部署在发布前就跟主干升级。** 因此这条约束是确定的（设计 §16.5、决定 46）：

- 账本结构版本 3 在第一次有真实账本升级到它之后冻结。冻结前发现缺列，可以往版本 3 的迁移里加；冻结后（含发布前）的任何结构变更都另起迁移，版本 4、5 依次递增，已被真实账本应用过的迁移不修改、不合并。
- 主干上哪一个提交第一次被真实账本应用，计划里要能看见：建议把"账本结构版本 3"节点的合入作为一个里程碑，合入前把各组已知的表与列一次收齐；之后的节点若要改结构，各自带一个新迁移，并在节点说明里写明。
- 发布物的 `schema.ledger` 取发布时主干上的最新版本，可能大于 3（附录 B.5）。
- 升级演练（第 5 节）验证整条迁移链：从版本 2 升到主干最新版本，以及从每个已冻结的中间版本升到最新。每冻结一个版本，账本夹具相应多一份。

## 2 验收要点

### 2.1 替身

现有的 `MODEL_STUB`（`ACT-ENV-04`）是一个按脚本返回内容的对话补全替身，按调用顺序出牌。v0.2.0 的级联里，同一道题会被两级各答一次，调用顺序还会随批量、复用和重判而变，这个替身不够用。需要两个替身，建议都放进 `flow-env-baseline`：

**分类端点替身（建议标识 `CLS_STUB`，新增）**

| 要求 | 用来验什么 |
|---|---|
| 讲 `probability-judgment/1`：整批请求、逐题 `p_yes`、`probability_source` | 协议客户端 |
| 按题目内容（模板名、输入里的关键字或来源事件 id）配置概率，不按调用顺序 | 不确定带的三个去向；影子打分；按分数排序 |
| 可配置单题错误：`input_too_large`、`unsupported_question`、`internal`，以及漏答 | 单题错误交下一级，同批其他题不受影响 |
| 可配置整批错误：400、401/403、408/504、413、429、5xx，以及协议标识不符、返回 `self_reported` | 整批错误的处置；自报概率被拒 |
| 可注入时延 | `timeout_ms`；web_only 初筛不等待 |
| 记录每一批收到的完整请求体与每批题数 | 批量不超过 `max_batch`；外发范围裁剪；`material_truncated` |

**对话端点替身（升级 `MODEL_STUB`，替换原实现）**

| 要求 | 用来验什么 |
|---|---|
| 区分判断题与生成请求（按模板名或结构化输出的 schema） | 同一个替身同时服务判断型的对话后端和生成型 |
| **同题重答**：对判断题按题目内容配置 `answer` 与 `sufficient`，与分类端点替身用同一套匹配键 | 落入不确定带的题由对话端点重答，且两级答案可以不同 |
| 记录请求体，能断言"收到的问法和输入与分类端点那一级相同，且不含上一级的答案" | 同题升级的定义（设计 §8.3） |
| 可配置：`sufficient: false`、不符合 schema 的输出、超时、5xx | 各级未定取保守默认并标"把握低"；起草失败不挡路 |
| 可返回首个输出 token 的对数概率 | `chat-logprobs` 的换算路径（是否开放由 `SPIKE-LOGPROB` 决定，替身先具备） |
| 保留原有的按脚本返回生成内容的能力 | 起草、抽取、卡片文案、简报等已有流程不回退 |

**测试时钟（建议标识 `TEST_CLOCK`，新增，主会话定）**

到期、跟进梯度、静音、登录锁定、链接过期这类验收要让时间往前走。静态链接的 Go 二进制不吃 libfaketime；改宿主系统时钟（`date -s`）会影响同机其他服务，现有执行机上也没有可随手开的一次性虚拟机。所以不靠环境改时间，由 APA 自己提供一个只在测试构建里存在的时间源：

| 要求 | 理由 |
|---|---|
| 代码里已有的 `Now func() time.Time` 注入点（`api/core`、`kernel/background`、`kernel/webhook`、`kernel/runidentity`、`kernel/attention` 等）统一接到一个时钟提供者，不再各自回落 `time.Now` | 一处换时间，全进程一致 |
| 测试时钟只在带构建标签（如 `apa_testclock`）的二进制里编译进去；发布物不带这个标签，`apa version` 里显示是否为测试构建 | 发布物里不存在改时间的入口 |
| 测试构建从 `APA_HOME` 下一个文件读偏移量，只能往前调，每次调整记一行服务日志，`apa serve` 不用重启；不新增 Event 类型 | 只进不退，验收可回放，不动账本契约 |
| 内核时钟循环在偏移量变化后立即重新计算到期，不等下一个 tick | 推进后的到期立刻可观察 |

这需要一个开发节点，放在 W0 之后、依赖时钟的验收之前。验收里凡是推进时间的步骤都用同一种方法：测试构建 + 写偏移量，T0 取该次运行开始时的时间。

`STUB_HARNESS`（`ACT-ENV-05`）不变。另需一份**账本夹具**，见第 5.1 节。

## 5 对已有数据的升级与回退要求

已有部署的账本应用过 v1、v2 两次迁移，有七个来源和数百条未判定的来源事件。下面是验收必须覆盖的要求，对应设计 §16.5 与决定 43–46。

### 5.1 账本夹具

各组验收与门槛 1、2 用一份**合成的** v0.1 结构账本，不用真实数据。它要包含：

- 已应用 v1、v2 迁移的结构；
- 若干来源（含邮件、日历、代码托管、自定义脚本），`outbound` 与 `default_project` 都不存在；
- 数百条积压，覆盖：`unjudged` 且原因为 `model_unavailable`、原因为 `undecided`、原因为空；`expired`；其中约一成是规则可以直接处置的结构化事件；
- 若干已有的 `run.finished`（`category: judge`）事件；
- 带 `model_endpoint` 的策略版本；开启与未开启 `threshold_judge` 的各一份；
- 规则模式记录：未动过的内置提醒类规则（`observe`）、本人切换过的规则；
- 一个覆盖内置包、带 `confidence_threshold` 的用户包；
- 若干在 `waiting`、已排跟进定时的事项；若干登录会话；
- 补救旧级联误丢用的对照组：若干由旧级联判断处置为 `ignored` 的事件（带 v0.1 的 `run.finished`，`category: judge`，没有判断记录），分布在不同时间与来源；另有被规则 `ignore` 出口忽略的、被本人忽略的事件，它们不应被放回。

每冻结一个账本结构版本（1.2），从它派生一份同内容的夹具。真实账本只在本机升级验证（设计 §20.4 清单 L1–L5）里由本人使用，不进仓库、不进验收环境，OMAC 不接触。

### 5.2 升级必须满足

| 要求 | 验法 |
|---|---|
| 不丢数据 | 升级前后各表行数不减 |
| 不改写历史 | 升级前已有的每条 Event，升级后载荷的哈希不变；序号连续，升级只在末尾追加（规则模式切换等） |
| 旧事件可回放 | 对升级前的事项与判断执行 `apa why`，结果可读 |
| 旧配置可用 | 不改任何设置，生成端点照常工作；已存的策略版本逐字节不变 |
| 升级本身不触发重判 | 升级完成后、本人操作之前，积压的处置分布不变；`unjudged_rejudge_days: 0` 的继续冻结 |
| 默认值变更留痕 | 每条被切到 `auto` 的规则各有一条 `rule.mode_changed`，操作者 system；本人切换过的不动 |
| 被拒的用户包有去处 | 同名内置包生效；健康视图与 `apa doctor` 列出要改的字段 |
| 预检只读 | `apa doctor --upgrade-check` 运行前后数据目录没有任何变化，并报告：结构版本差异、会被拒的包、未选外发范围的来源、缺 `public_url` |
| 失败可退 | 在迁移中途注入失败：整体回滚，账本与升级前逐字节一致，旧版本二进制仍能打开 |
| 自动快照 | 迁移前在 `<APA_HOME>/backups/` 下有一份快照，`apa backup verify` 通过 |
| 版本闸 | 旧版本二进制打开版本 3 的账本时拒绝启动，不带着看不懂的数据运行 |
| 迁移链 | 从版本 2 的夹具升到主干最新版本、从每个已冻结版本的夹具升到最新，各自满足本表全部要求；已冻结版本的迁移文件与冻结时逐字节一致 |
| 插件同步 | 只升内核不升插件时，凭原话的代答被拒且 `apa doctor` 指出原因；读取与回执不受影响 |
| 登录 | 已有口令可登录；升级前的登录会话失效 |

### 5.3 积压必须能被新的级联重判

| 步 | 要求 |
|---|---|
| 只跑规则 | 夹具里的结构化事件被处置，能挂靠的挂靠；两个模型替身零调用；其余积压原样 |
| 影子打分 | 每条剩余积压得到一条带 `shadow` 的判断记录；处置分布不变；来源页可按分数排序 |
| 定不确定带 | 只能在 Web 改，记 Event |
| 放开重判 | 含已 `expired` 的和原因为 `undecided`、为空的；按分数从高到低；每天进入建议流的数量不超过 `backlog_release_per_day`；每次放回各有一条 `inbound.requeued`；全部放完后积压里只剩本人明确留下的 |
| 没有判断端点时 | 跳过中间两步，由对话端点逐条回答同一道初筛题，同样受每日上限约束 |
| 外发范围 | 来源未选外部范围而端点在外部时，重判把事件记为 `outbound_unset` 而不是送出 |
| 放回旧级联忽略的事件 | 只命中夹具里旧判断忽略的那一组，对照组不动；放回后经上面四步重判，受每日上限约束；升级本身不放回任何事件 |

### 5.4 回退

- 路径只有一条：停止服务，旧版本二进制加升级前快照。验收要实际走一遍，并断言回退后的账本与升级前一致（行数、最大序号）。
- 升级之后写入的数据不在快照里。回退前先用新版本做一次备份并保留导出目录；验收里检查这份备份可校验。
- 迁移不提供逆向脚本，不要为它建节点。
