# 升级、回退与本机验证

v0.x 期间次版本可以包含需要迁移的变更。升级前先读[变更记录](changelog.md)里“需要迁移的变更”。

## 备份与恢复

| 命令 | 行为 |
|---|---|
| `apa backup create [--out <目录>]` | 运行中也可执行；账本用在线备份导出一致快照，另复制 `blobs/`、`packs/`、`config.yaml`、`sources.json`、`declarations/`、`sources/`、`webhook-keys/`；不含 `runs/`、`run-credentials/`、`logs/`。目录权限 0700，带清单（版本、各模块数据结构版本、文件哈希）。备份含来源凭据与接收密钥明文，`--no-secrets` 时不含 |
| `apa backup verify <备份>` | 核对清单哈希，检查账本副本完整性与 Event 序号连续 |
| `apa backup restore <备份> --home <目录>` | 只恢复到空目录，不覆盖正在使用的数据目录；备份的数据结构版本高于当前二进制时拒绝 |

外部工具的配置和凭据不在备份范围，换主机需重新认证。

## 升级

1. **备份**：先 `apa backup create`，再 `apa backup verify`。
2. **预检**：用新版本运行 `apa doctor --upgrade-check`。它只读，报告数据结构版本差异、会被拒绝的用户能力包、未选外发范围的来源、缺少的 `public_url`（监听非本机地址时）。
3. **替换**：停止服务，替换发布包（先核对哈希清单）。宿主插件**须与内核同时升级**。
4. **启动**：新版本的 `apa serve` 发现数据结构版本较旧时，先在 `<APA_HOME>/backups/` 下自动留一份升级前的自动快照（账本与配置），再迁移。迁移只增不改：新增表与列，不删除、不重写已有的行，也不改写已有 Event 的载荷。任何一步失败则整体回滚并拒绝启动，数据不变。
5. **确认**：`apa version` 的数据结构版本与发布物声明一致；`apa health` 无错误；`apa doctor`。迁移后的默认值变更作为普通命令落账并记 Event（操作者 system），不静默生效。

数据结构版本随发行只增。旧版本的二进制拒绝打开版本更高的账本，不带着看不懂的数据运行。已有部署跟随主干升级时，已被真实账本应用过的迁移不会被修改或合并，结构变更另起迁移、版本依次递增。

### 从 v0.1 升级时已有数据怎么处置

| 已有数据 | 升级后 |
|---|---|
| 事项、项目、材料、Event、投递、运行记录 | 原样保留，新增字段为空 |
| 来源事件与积压 | 原样保留，处置不变；升级本身不触发重判。`unjudged_rejudge_days` 为 `0` 的继续关闭自动重判；积压的放开由你显式触发 |
| v0.1 的判断留痕 | 原样保留、可回放，不计入校准统计 |
| 策略里的 `model_endpoint` | 读取时等同 `generate_endpoint`，位置按 `external`；你下一次在 Web 保存端点设置时写成新字段 |
| 来源登记 | `default_project` 为空；`outbound.local` 为 `full`，`outbound.external` 为未选择，使用外部端点前每个来源要选一次 |
| 规则模式 | 内置提醒类规则若仍是初始 `observe` 且你从未切换过，升级时切到 `auto` 并逐条记 `rule.mode_changed`；你切换过的、覆盖包里显式写了 `observe` 或 `off` 的不变；动作类规则不变 |
| 覆盖内置包的用户包 | 用到已移除字段的包被拒绝加载，内置包生效，健康视图给出要改的字段 |
| 运行配置 | 旧键全部有效；监听非本机地址的部署升级前要补 https 的 `public_url` |
| Web 口令与登录会话 | 口令继续有效；已有登录会话全部失效，重新登录一次 |
| harness 插件 | 须与内核一同升级，否则凭原话的代答被拒（退出码 23） |
| 渠道 ext 与事件订阅 | 协议版本不变；自行实现的渠道 ext 要能处理 `item` 为空的提醒投递；订阅方遇到不处理的事件类型应跳过并推进游标 |
| 被旧级联忽略的来源事件 | 原样保留为 `ignored`；你可按时间段把它们放回积压（先预览再执行，幂等），交新的级联重判 |

## 回退

迁移不可逆向执行，所以回退**只有“恢复快照”这一条路**：

1. 回退前先用新版本做一次 `apa backup create`，并保留导出目录——升级之后写入的数据不在快照里，需要时手工补录。
2. 停止服务。
3. 用旧版本二进制加升级前的自动快照（`<APA_HOME>/backups/` 下）恢复：`apa backup restore <快照> --home <空目录>`，再把服务指向该目录。
4. 旧版本二进制会**拒绝打开**升级后的账本，不要试图直接用旧二进制打开新账本。

## 升级后本机验证清单 L1–L12

真实模型端点、真实宿主、真实渠道账号与测试邮箱日历仓库的验证不在开发验收里自动化，由你把自己的部署升级后在本机执行（设计门槛 5）。升级前先按上面做一次备份；会改动数据的演练（回退）只在备份恢复出的副本目录上做，不动正在使用的数据目录。“测试邮箱、测试日历、测试代码仓库”指专为验证准备、不含他人真实往来的账号与仓库。

| # | 验证什么 | 怎么看结果 | 通过标准 |
|---|---|---|---|
| L1 | 升级预检只读 | 升级前用新版本运行 `apa doctor --upgrade-check`，前后各对数据目录做一次文件清单与哈希 | 数据目录没有任何变化；报告列出结构版本差异、会被拒绝的用户能力包、未选外发范围的来源，以及（监听非本机地址时）缺少的 `public_url` |
| L2 | 升级本身 | 停止服务、替换发布包、启动；查看 `<APA_HOME>/backups/`、`apa version`、`apa health`；对升级前已有的几条事项与判断执行 `apa why` | 自动快照存在且 `apa backup verify` 通过；结构版本与发布物声明一致；各表行数不减、Event 序号连续；旧事项与旧判断可回放；不改任何设置时生成端点照常工作；本人操作前积压的处置分布不变；被切到 `auto` 的提醒类规则各有一条 `rule.mode_changed`，本人切换过的不变 |
| L3 | 回退 | 在备份恢复出的副本目录上，先用旧版本二进制打开升级后的账本，再用旧版本二进制加升级前快照启动；对比行数与最大 Event 序号 | 旧版本拒绝打开升级后的账本；用快照恢复后与升级前一致 |
| L4 | 外发范围与登录 | 在 Web 为每个来源选外发范围；用已有口令登录，查看在线会话 | 选定之前，规则判不了的新事件记 `outbound_unset`，健康视图与 `apa doctor` 有提示；选定后自动重判；已有口令可登录，升级前的会话已失效 |
| L5 | 积压放开与不确定带的起始值（`ACT-BKL`） | 在真实积压上依次执行只跑规则、影子打分；在"判断与校准"页看分数分布；从两端各处理一批后定不确定带，再放开重判，连续观察至少两天 | 只跑规则时零模型调用；影子打分不改处置；每天进入建议流的数量不超过 `backlog_release_per_day`；分数分布、带内占比、两端各一批的误判数有记录并写回 §8.9 |
| L6 | 补救旧级联误丢的事件 | 选一个时间段先预览，再执行；之后按 L5 的步骤放开；对同一时间段再执行一次 | 预览条数与执行条数一致，放回时没有模型调用；放回的事件经新的级联重判并受每日上限约束；第二次执行放回 0 条 |
| L7 | 第一档：只有内核 | 在一个不配模型端点、不接宿主的实例上（可用备份恢复出的副本目录并停用来源拉取），走一遍场景十二与跟进到期 | 与 §2.4 第一档一致：工作台可用，等待到期即有提醒，规则判不了的事件留在积压 |
| L8 | 第二档：加模型端点 | 接上真实的生成端点与至少一个真实的分类端点（原生协议、转换程序或对数概率换算三者之一）；触发全部内置模板；按 `SPIKE-CLS-BATCH` 的方法测分类端点的时延；有条件时按 `SPIKE-LOGPROB` 的方法取样 | 内置模板的结构化输出符合 schema，不符合的按 §8.7 退化并有记录（`SPIKE-STRUCT`）；`timeout_ms`、`max_batch`、`max_material_chars` 的默认值得到确认或给出修改值；结论写回 §21.3 所列位置 |
| L9 | 第三档：加首批宿主 | 宿主插件与内核一同升级；新开会话看注入；在私聊会话与多人会话里各发起一次凭本人原话的代答；委派一件事并等回执；起一次一次性命令的后台运行，以及插件声明过的唤醒运行 | 注入按项目作用域，不用重述背景；私聊会话上报 `direct` 并被接受，多人会话被拒（退出码 23）（`SPIKE-SESSION-KIND`）；回执回到原事项；运行上下文到达工具与终端子进程，不同运行互不串值（`MEAS-HOST-CTX`）；唤醒期间该 delegate token 不能代答；结论写回附录 A.5 |
| L10 | 接入后的一个工作日（§1.4） | 用真实模型端点、首批宿主、即时通讯渠道、测试邮箱、测试日历与测试代码仓库，按 §1.4 的时间线走一天 | 每个时间点的结果与 §1.4 一致；入站结论能用判断记录说明由哪一级定案、是否把握低；跟进提醒不需要先切规则模式；"今天"视图、计划日期、进展与建议的批量处理可用；结束时做一次抽检，`apa doctor` 没有错误级结论 |
| L11 | 续保（§3.11） | 用测试邮箱与测试日历走 §3.11 全程 | 邮件与日历事件按来源的默认项目归入；续保邮件的回信回到原事项（`MEAS-MAIL-THREAD`，结论写回附录 D）；诱导语只作资料、不产生投递；付款决策只能在 Web 确认，`apa why` 能回放全链路；多人会话里凭原话的代答被拒 |
| L12 | 例行任务与远程访问 | 建一个 `run` 模式的例行任务实例并等它到点；Web 暴露到本机之外时，在手机浏览器上打开一次导出文件里的动作链接 | 任务型读到实例的任务说明并把结果写回事项（`SPIKE-ROUTINE` 的 `run` 部分）；动作链接在未登录时先登录再到确认页 |

“中心 APA 加多台 harness 主机”本版仍不验，记为“本版未执行”，有第二台 harness 主机时补验。本机升级验证发现的问题按缺陷登记，修复后重新执行受影响的条目。
